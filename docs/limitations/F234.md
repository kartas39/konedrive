- **F234. What the helper's missing write probe, its version check and its panic containment leave open**
  (`konedrive-helper/src/registration.rs`, `connection.rs`, `events.rs`, `outbox.rs`;
  `konedrive-proto/src/lib.rs`; quality findings `HE7`, `PR1`, `HE8`).
  - **The helper probes no filesystem feature.** It used to run the daemon's probe again, as
    root, at a first registration (a nameless file: a write, a hole, a `user.*` attribute, a
    lease). Under the shipped unit that write was refused almost everywhere a sync folder can
    be, and the helper logged "the helper's own sandbox stopped the feature probe" and went on.
    Not everywhere: `ProtectSystem=strict` and `ProtectHome=read-only` make read-only what is
    mounted when the helper starts, not a filesystem mounted under it later (`systemd.exec(5)`),
    and the helper starts before the display manager. For a home of systemd-homed or
    `pam_mount`, an automount or a removable drive, only the missing `CAP_DAC_OVERRIDE` stopped
    the write, and not in a folder that "other" or an ACL lets root's uid write to: there the
    helper's probe did run, as root. Either way the daemon's probe, run as the user before it
    asks the helper, had passed already, and a peer that is not the daemon could always choose
    a folder where the helper's was skipped. The helper's is removed, with that log line and
    its throttle key. It still refuses a filesystem by its type (`fstatfs`: network and FUSE
    filesystems, FAT, exFAT), at a registration and at its start. What that leaves:
    - a helper whose write the unit does not stop (a folder as above; the VM suite's helper;
      one started by hand) no longer refuses `EOPNOTSUPP` a local filesystem without hole
      punching, `user.*` attributes, `O_TMPFILE` or leases, nor `EIO` a folder its probe could
      not write to. Only a peer that skips the daemon's probe reaches that, and it registers a
      folder of its own that it cannot use;
    - a folder that already carries a root id is probed by nobody when it is brought up (F31):
      the daemon skips its probe there, and the helper's ran only for an id it did not hold yet,
      and only where the unit did not stop its write.

    Reasoned from the unit and the code; the unit run (`tests/vm/run.sh unit`) no longer sets
    the probe's refusal aside, because there is none.
  - **`Hello` is optional.** A `Hello` that names another protocol version now ends the
    connection, with no `Ack` (it was answered `EPROTO` and the peer served on). A peer that
    sends no `Hello` at all is served, whatever it speaks: the version is checked only when it
    is said. The daemon always says it, as its first call, and hangs up itself on a `Welcome`
    with another version, so it never sees the helper's side of the check; a daemon and a helper
    of two versions fail the daemon's connection with "the helper greeted with protocol version
    …", as before. So the daemon's own text for a refused `Hello`, "the helper rejected our
    protocol version" (`konedrived/src/helper/link.rs`, `handshake_error`), is no longer reached
    with this helper: it is left as it is. Requiring a `Hello` before anything else would change what the helper accepts
    from the VM suite's bare clients and is not done. Measured (VM `a Hello with another
    protocol version closes the connection`).
  - **What `ToHelper::validate` does not bound.** It checks the two fields that have a form:
    the `root_id` of a `RegisterRoot` and the handle of an `OpenByHandle`. The `root_id` of an
    `UnregisterRoot` may be any string up to the datagram (64 KiB): it is only compared with the
    ids the helper holds, and shown escaped and cut. The `errno` of a `HydrateDone` is any
    `i32`, clamped by the helper. A datagram longer than 64 KiB is refused as truncated and ends
    the connection; before, its head was parsed, which failed as JSON in practice.
  - **A panic the helper survives costs more than the event it came from.**
    - In the event loop, the open in hand and every event read with it and not yet handed over
      are denied `EIO`, the helper's own opens among them (an `OpenByHandle` then answers the
      daemon `EIO`). Handling the rest normally after a panic was not chosen: the batch is
      given up, the next read goes on.
    - Every permission event the loop has read is made a `PendingOpen` before anything else is
      done with it (`owed`), so a panic over it, or while giving it up, denies it `EIO` as it is
      dropped. Only the two reads before that (its mask and its pid) see it bare.
    - The helper's error line for it is throttled (one in five seconds, with a count; the last
      count of a burst is not written). The panic's own message, from the panic hook, is not:
      something an opener could make panic there would write one for each open.
    - On the accept thread, the connection in hand is closed, and nothing is accepted for one
      second (`ACCEPT_RESTART`, chosen, not measured); a daemon that connects meanwhile waits in
      the listener's backlog of 16. A panic that repeats writes one error line a second, and the
      panic's own message with it.
    - On a connection's writer thread, the connection ends as it does for a failed send, and its
      openers are denied `EIO`.

    Measured: VM `a panic in the event loop denies the open in hand and keeps the helper`, `a
    panic on the accept thread closes one connection and the next is served`; the rest of a
    batch and the writer by unit tests (`events/tests.rs`, `outbox/tests.rs`).
  - **What still ends the helper** (and so releases every suspended open as allowed, Z1): a
    panic in the event loop outside the handing over of a batch (the `poll`, the read, the
    throttled log lines), a panic while another is unwinding, an error of the group's own
    descriptor, and anything at the start before the loop. The thread that writes the last
    count of a burst of refusals (`konedrive-log`) is not guarded: if it dies, those counts are
    no longer written, and nothing else changes.
