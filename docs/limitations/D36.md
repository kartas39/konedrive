- **D36. The store's schema has a number for every change, and what that leaves.** DEBT and
  FRAGILE, *measured* (`konedrive-tree`'s `schema::tests`, `outbox::encoded::tests`) and
  reasoned, open. A store is brought from schema 3, 4 or 5 to 6 by numbered steps, each in a
  transaction (`konedrive-tree/src/schema/migrations.rs`); a new store is created at 6 from
  one description (`schema.rs`). Schema 5 is schema 4 with everything earlier builds added on
  every open without a number; schema 6 keeps a row's snapshot in columns
  (`snapshot_size`, `snapshot_mtime`, `snapshot_mtime_nsec`, `moved_out`) and has no trigger
  (quality findings `TR3`, `TR4`). What is left:
  - **A downgrade rebuilds the store.** A build older than schema 6 does not know the version
    and rebuilds from a full listing: the outbox goes (uploads start again from what is on
    disk, a delete not sent yet is forgotten and its item comes back, `writes.md` §5.1), and
    so do the activity log and the conflict list (F24). While everything was added under the
    number 4, an older build opened a newer store as it was.
  - **A step that fails keeps the folder from opening.** Its transaction is rolled back and
    the error is returned, as an error of the upgrade on open was before: only a file that is
    not a database, or a version no step starts from, is rebuilt
    (`schema::tests::a_step_that_fails_leaves_the_store_and_its_outbox_as_they_were`). What
    the user sees: the daemon runs; that one folder has the blocking trouble "the tree store
    cannot be opened: …" and is locked read-only; other folders are unaffected; it is tried
    again at the next bring-up. A step that fails every time (a store in a state no build
    left) fails at each of them until the store is removed by hand. Reasoned, but for the
    test.
  - **A row is removed from the outbox in one function** (`outbox/stored.rs` `remove`), which
    leaves its opening's record behind (`upload_openings_left`), where a trigger did it for
    every `DELETE`. A `DELETE FROM outbox` written anywhere else would leave a record in
    `upload_openings` for a `seq` no row has: its window stays, so an empty placeholder at
    that name could still be taken for this folder's. Nothing checks that there is no such
    statement. `left_at`, from which the week a left record is kept counts, is the wall clock
    read inside that function, as the trigger read it: a test cannot set it.
  - **What the schema-4 fixture is.** `schema/tests/v4.sql` is a store the build of `dev`
    at `8ea40f6` wrote through its own functions, dumped as SQL: the shape every build since
    the leaving mechanism (issue #104) leaves. `v3.sql` is written by hand from the history of
    the schema (version 3 as first created, the openings of before issue #89): no old build
    made it, and the states in between are covered by the step adding only what is missing,
    not by a fixture each.
  - **A snapshot whose text said nothing** (no build wrote one) is dropped by the step to
    schema 6; the worker takes it again and gives up the session opened for it. Before, such
    a text still gave the sums a size (what stood before its first space).
  - **A marker no build writes blocks the row** (`unreadable marker "…"`), as an unreadable
    kind or state does: listed under "Needs you: each file" with the raw text (F200).
  - **Paths still have two encodings** (`TR3`): `outbox.rel` and `local_skipped.rel` are text
    when the path is UTF-8 and bytes otherwise, `leaving.rel` always bytes. A range over
    `outbox.rel` is therefore asked twice (`rows_under`).
  - **An unknown `placement` or `kind` in `items` still reads as placed and as a file**
    (`TR6`), and SQL, which compares the text, takes an unknown placement for not placed.
    Left on purpose. Since every change of a stored word is now a new schema version, and a
    store of a newer version is rebuilt, only a damaged store has such a row. Failing closed
    there has no good form: an error on read leaves the folder in error with nothing that
    heals it (the store opens, so it is not rebuilt), a rebuild at open costs the outbox for
    one damaged cell and a scan of `items` at every start, and reading it as not placed would
    start the leaving mechanism on an object the damage, not OneDrive, took out of the tree.
    Reasoned, not traced further.
