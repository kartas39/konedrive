- **F237. What the one shape of the move out leaves: a file in the Trash whose free-up was cut short goes without a second look, and the Trash rule was not run against the real helper again**
  (`upload/move_out/tidy.rs` `fate`, `tidy_dirs`, `Walked`; `upload/move_out/cases.rs`
  `trashed_file`, `trashed_folder`; `upload/move_out/dropped.rs` `Tidy`; `upload/move_out/reach.rs`
  `Reach`; quality findings `UP8`, `UP12`; F123 for the dropped rows). FRAGILE, *reasoned* in
  part, open. The Trash case of a `move-out` row and the tidying after dropped rows follow one
  rule now, written once: a downloaded file stays, stripped; a file that is not downloaded, or
  is between the two (a fill or a free-up cut short), goes; a directory of the item is unmarked, stripped, and removed if left empty. What that
  rule decides differently from the two copies it replaces:
  - **A file in the Trash that reads `dehydrating`** (a free-up cut short by a crash; no
    free-up is under way, since the row holds the file's lock) is removed and its item
    deleted in OneDrive, as a placeholder is. Before, the row waited (`not-local`) for as
    long as the file stayed so, which nothing ended: no recovery looks outside the folder.
    The content the free-up began on is in OneDrive's recycle bin: a free-up only starts on
    content OneDrive has. The file itself may still hold all of it: a free-up cut short
    between its mark (`hydration/dehydrate.rs`, `mark_dehydrating`) and its punch has
    punched nothing. **What can be lost, accepted:** the daemon dies after that mark and
    before `ClearIgnore`, the user edits the file in place (the examination reads
    `dehydrating` as content it cannot tell, and records no upload), then sends it to the
    Trash: the edit goes with the file, and OneDrive's recycle bin has the version before
    it. No guard: the user sent the file to the Trash, and a delete is a delete; in the
    folder, startup recovery punches such a file as well. *Measured* on the host (`upload::tests::move_out::the_trash_takes_placeholders_without_a_download`);
    that the lock proves no free-up is running is *reasoned* (`folder/locks.rs`: the fill,
    the free-up and this step take the same per-inode lock).
  - **A folder of the item that stands inside an entry of the Trash**, not as the entry
    itself, is removed when it is left empty, as its own subfolders always were. Before, it
    stayed there, empty and stripped. The entry and its `.trashinfo` are the user's and stay.
  - **A handle of another filesystem** (`ESTALE` while the handles the store recorded are
    not the folder's filesystem's) is told apart from "gone" for the re-marking and for
    the tidying too, not only for a row's step: the re-marking asks again at the next look
    (before, it took the row for done on that helper connection), and the tidying says in
    the journal that it did not reach the object (before, it said nothing). The re-marking
    is *measured* (`upload::tests::move_out::a_changed_filesystem_takes_the_handles_again_and_deletes_nothing`);
    the tidying's part is a journal line and has no test.
  - **Not run against the real helper**: `tests/vm/run.sh quick` covers the row's cases
    with real marks; the two changes above are covered on the host only, with the fake
    helper.
  - **Not covered by a test**, as before: a moved-out file open for writing (the lease
    probe), a place that cannot be proved (`moved-out-place-unknown`), and an object that
    carries another item's id (`another-item`).
