- **F200. A bad upload's item is remembered beside its row, and blocked rows are listed per file whatever their reason**
  (`konedrive-tree/src/outbox/worker.rs` `outbox_bad_item`, `upload/content.rs` `clear_bad_item`,
  `upload/kept_back.rs` `group_of`; quality findings `UP2` and `UP3`). What is left:
  - The item OneDrive made of a new file with other content than was sent is remembered in the
    outbox row's `bad_item` column, with the cTag the upload's answer gave (`bad_item_ctag`; its
    eTag, `bad_item_etag`, only when the answer has no cTag), until it is deleted, found gone,
    found changed, or adopted. It goes with the row, and a row can
    leave before that delete has gone through:
    - The file is removed, or moved where no row looks (`steps::never_uploaded`). `landed_away`
      deletes what stands at the row's name if its size and time are the ones sent, which a bad
      item can match; one that does not match stays.
    - `outbox_drop_unsent` makes a later row of the same object the `create`: that row has no
      bad item, and its upload meets the item with a `409`, decided as any other holder of the
      name (a conflict copy, unless the content is the same).
    - An examination's detection cancels the row (a `create` deleted or moved out before it was
      sent).
    - The outbox is dropped by force (`outbox_drop_all`, from `drop_pending_uploads` and `turn` in
      `sync/write_mode.rs`).

    An item that stays is placed in the folder by the next cycle: a file with content the user
    never wrote. The same was true while the id was kept in the reason.
  - Whether the item is still the bad upload is decided by its content tag: it is read again,
    and deleted (with the eTag just read as the guard) only while its cTag is the remembered
    one. An item whose content someone changed since, or whose delete answers `412`, is left
    and forgotten; the file then goes up against the name's holder as against any other, most
    often as a conflict copy. What this does not see:
    - A rename or a move of the bad item by someone else moves its eTag, not its cTag: the
      item is deleted where it now is. The eTag cannot be the test, since OneDrive moves it
      by itself with no change of content.
    - If OneDrive itself moves the cTag of an item after an upload, the bad item is taken for
      changed and left.
    - When the answer carried no cTag, its eTag is compared instead, and an eTag OneDrive
      moved by itself then leaves the item.
    - With no tag remembered — a row an older version wrote (`hash-mismatch:<id>` in its
      reason), or an answer that carried neither tag — the item is deleted as that version
      deleted it, with the tag just read as the guard: one changed by someone since goes to
      the recycle bin. This is the old weakness, kept for those rows only, so that a row in
      that state at the upgrade still goes up under its own name.
    - The delete `finish` asks right after the upload uses the answer's own eTag (its cTag
      when it has no eTag). With neither, the `If-Match` is empty, as it was before: what
      OneDrive answers to that was not measured (F235); an answer that is not success or `404`
      leaves the item remembered for the next run.
  - If the store cannot record the bad item, its delete is still asked for; if both fail, the
    item stays unremembered and the row is settled with the store's failure.
  - The move of an older row's id into the column (`outbox/schema.rs`) skips a row that already
    has a bad item: after a downgrade and a second upgrade such a row keeps the old reason
    `hash-mismatch:<id>` until its next settle, shown as stored.
  - `bad_item` is not a field of `OutboxRow`: every run of a `create` reads it with one more
    query, and the move above runs each time the store is opened.
  - A blocked row whose reason is in no other group is listed under "Needs you: each file",
    also for reasons the user can do nothing about but change the file again (`no-name`,
    `no-item`, `no-guard`, `no-handle`, `bad-handle`, `another-item`, `state-unreadable`). These
    have a sentence that says only that konedrive's record of the change is incomplete. A row
    the store cannot read (`unreadable kind "…"`, `unreadable state "…"`) and a blocked row with
    a reason the table does not know are listed there with the raw string.
  - The group follows the row's state, but `NotUploadedFiles(reason)` still chooses files by the
    reason's key alone: a key that had both blocked rows and waiting ones would list all of them
    under each of its two lines. No reason is written in both states today.
  - Four keys are still whole sentences (`changed in OneDrive again and again`, `changing in
    OneDrive again and again`, `the upload session ended twice`, `not allowed now`), and a key is
    cut from a reason at the first `: ` only when what is before it is in the table. The typed
    reasons of the quality plan's `B1` keep both, since the spellings are stored and sent
    (`D34`).

  - A `412` on the delete of an item whose content tag still matched leaves the item and forgets
    it, though its content is still the bad upload: the eTag moved between the read and the
    delete. The file then meets it with a `409` and most often becomes a conflict copy. The
    window is the moment between two requests; `file_changed` (`upload/steps/meta.rs`) reads again
    in the same case, this does not. Reasoned.
  - That the cTag of an upload's answer is the string a later read of the item returns is taken
    from how `file_changed` already compares them; it was not measured against OneDrive. If it
    did not hold, every bad item would be taken for changed and left.
