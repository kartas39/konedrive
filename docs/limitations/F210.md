- **F210. An entry the examination is refused to open, strip or read is passed over, and the
  user is not told which** (`local/examine.rs` `entry_io`; `local/watcher/mod.rs`;
  `upload/steps/shared.rs` `dir_id`; `folder/disk.rs` `attr_by_name`; quality findings `LO3` and
  `LO13`) — what the policy does, and where it stops:
  - **What is passed over.** After the listing, an open, a strip or a read of one entry that
    is refused with `EACCES` or `EPERM` (another user's file, an immutable one), and `EIO`
    while an open file's content is read for its hash. The entry is not examined in that run:
    nothing at its place counts as missing, it gets no row, a copy that kept its attributes
    is not uploaded as new, and what was listed inside a directory that was not stripped
    (refused, or gone while the run looked at it) gets no row. An entry gone since it was
    listed is skipped, as before.
  - **What still fails the whole batch**, as before: any other error at those places
    (`EMFILE`, `ENFILE`, `ENOMEM`, `EIO` from an open, a name that is no longer a file), and
    every error of the listing phase except a refusal (`list.rs` `list_dir`: opening a
    directory, its `fstat`, reading its names; `run.rs` `read_entry` and `read_one`). One
    entry can still stop the examination there. The batch is offered again with a backoff of
    5 s to 600 s. `LastError` says so from the third failure in a row (`FAILING_AFTER`,
    chosen, not measured), and stops saying it when a batch passes, when the folder has no
    completed listing, or when the watcher stops. Since the next try can be 600 s away, the
    note can outlast its cause by that long; it says so ("every 10 minutes at the longest").
  - **The recheck.** All passed-over entries share one pending recheck. It comes 5 s after
    the first run that passed one over, and the wait doubles, up to 600 s, each time a recheck
    passes any over again; a recheck that passes none over starts it at 5 s again. An entry
    passed over by another run joins the pending recheck and does not move its time, so an
    entry that becomes readable, or a new one, can wait up to 600 s. A run writes one warning
    for all the places it did not examine (how many, the first twenty by name), unreadable
    directories included, which were one warning each; past twenty a place is named only
    with debug logging.
  - **Nobody tells the user which.** `Examined::unreadable` is read by nothing but tests, the
    entry is not in Not Uploaded, and `LastError` does not mention it. A file the user edited
    and the daemon may not open is not uploaded, in silence.
  - **A directory that carries another folder's id** (a copy that kept its attributes) is
    stripped by the examination only in a run that reads it, and only if it may. Until then a
    row below it is recorded with no parent, and the worker takes a parent's id from a
    directory on the disk only when the id is the directory's own: the base has it as a
    folder, and the directory is the object the base records for it. With no object to
    compare (the base records none, or the directory gives none), the directory counts where
    the base places the folder. A folder that waits to leave the folder is placed by the
    base, with its object, and gives its id as any folder does (F188). Otherwise the row
    waits, and so does an item moved into such a directory. One copy is still taken for the
    folder: one standing exactly where the base places a folder with no object recorded (as
    the examination takes it). Reasoned.
  - **What the user reads for such a row, and the way out.** The row is in the outbox list
    (`konedrivectl`'s and the window's) as waiting to be tried again, with its reason shown
    as the code `parent-not-in-onedrive` (A22: the worker's retry reasons have no sentence);
    it counts in `PendingCount` and in the waiting group of Not Uploaded. Neither `LastError`
    nor the outbox note mentions it, and the line that names the directory is written only
    with debug logging. It is tried every 30 s for as long as the directory keeps the id. The
    way out: remove the copy, or take the `user.konedrive.*` attributes off it, or make it
    strippable (give it back to the user, lift the immutable flag), so that the next
    examination that reads it strips it and uploads it as a new folder.
  - **The worker's check reads the base (`items`) alone, without the tree lock.** A folder a
    cycle places between its staging and its swap reads as not its own for that moment: a row
    with no recorded parent waits 30 s and then goes.
  - **A filesystem that holds no user attributes** (vfat, some FUSE mounts) answers
    `EOPNOTSUPP` to a read of one. That reads as "no attribute" in the examination's entries
    and in `Disk::probe`, with every caller of it (the reconcile, the worker's `dir_id`, the
    ignore rule). Narrower was tried: with only the examination and `Disk::scan` lenient, a
    vfat mount over a folder OneDrive has still failed every cycle (VM). That it is safe
    rests on three things: the root's own attribute is read through a descriptor, strictly,
    before every examination and reconcile; what is on another device than the folder is
    skipped before any id on it is used (F72); and the worker takes an id from a directory
    only when the base records that object. An attribute read through an open descriptor
    (`placeholder::read_state`, `read_item_id`) still answers the error; whether anything
    reads one on such a mount was not traced.
