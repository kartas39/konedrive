- **D38. The running parts of a folder's sync are beside its state, not in it.**
  DEBT · reasoned, planned (part 4 of `B5`, quality finding `SY3`). The folder's state is a type
  inside its lock (`sync/folder.rs`: the standing, the wanted mode, absent, down or up), but what
  runs for a OneDrive folder that is up is still held in fields of `SyncService`: `syncing` (the
  poller, the watcher, the outbox worker, the thumbnail filler), `store`, `source`, `tree_lock`,
  `kept_back`. So the types do not yet rule out a tree store or a content source that outlives its
  folder, a watcher without a worker, or a running sync on a folder that is down: those are kept
  apart by the code that holds a `Stopped` (`start_sync` starts nothing unless the state says the
  folder syncs; `change` stops everything first). `stop_sync` is built for the tests and the VM
  suite alone (`fault-injection`), and stops the tasks without the state lock. Whether a sync could start is said in
  the snapshot (`sync_trouble`), not in the state. What reads the folder without the lock reads a
  copy (`View`) made each time a change publishes: inside a change it is as old as the last
  `publish`, so a function that starts a part which reads it publishes first (`start_sync`, the
  switch of mode). The tests of `sync/` that still reach a field reach these: `syncing`, `store`,
  `tree_lock`, `kept_back`, and the private `nudge`, `nudge_full`, `wake_outbox`,
  `changes_in_store`.
