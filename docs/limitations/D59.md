- **D59. The check of the doc links sees a broken link, not a wrong one.**
  DEBT, *reasoned*, open.
  - `.github/workflows/structure.yml` runs rustdoc over the workspace, private items included,
    with `-D rustdoc::broken_intra_doc_links`: a link in a doc comment that resolves to nothing
    fails the pull request. By hand:
    `RUSTDOCFLAGS="-D rustdoc::broken_intra_doc_links" cargo doc --workspace --no-deps --document-private-items`.
  - A link that resolves to another item than the one meant passes. The case met: a module's
    file starts with `//!` and its `mod` line in the parent carries a `///` line. rustdoc then
    resolves every link of the file's `//!` in the **parent's** scope, so a bare name is looked
    up one level too high: `[`write`]` in `konedrived/src/panic.rs` resolved to the macro of
    `std`. Such a link is written with its full path (`crate::panic::write`), which holds in
    either scope; the next one written bare is caught only if the parent has nothing of that
    name.
  - Code under `#[cfg(test)]` is not documented, so the links in the doc comments of test
    modules and of the `testing` fixtures are not checked at all.
  - About fifty links go from a public item's doc to a private item. They resolve only because
    private items are documented, and rustdoc warns of each; the check does not fail on a
    warning, and the docs are never built another way.
  - Only the comments rustdoc reads are checked: a `//` comment, and a name in backticks that
    is not a link, can name a file, a function or a test that is gone. The reading pass of
    2026-10-05 was done once, by grep for names and markers; nothing repeats it.
  - The workflow pins the compiler by its own `RUST_VERSION`, a second copy of the one in
    `release.yml`: the two are moved together by hand.
