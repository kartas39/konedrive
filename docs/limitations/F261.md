- **F261. After the folder's filesystem changed, a move out whose object is not found where it
  went is given up, and what is left outside is not tidied.** LIMIT, *measured*
  (`local::tests::liveness::on_a_changed_filesystem_a_move_out_goes_on_where_its_object_is_now`).
  Open. When the handles are taken again (`local::handles::prepare`; a new disk, a snapshot
  rolled back; F121 (9)), each `move-out` row is looked for where its object was last proved.
  The recorded path is resolved first (it may lead through a symbolic link by now: a home
  copied to a new disk and its old path made a link), then opened with no link in it
  (`local::liveness::open_no_symlinks`), and the item id, the inode and the handle are read
  from that one descriptor. An object that carries the row's item id is the proof: the row
  takes its handle and the resolved place, and the user's move out goes on. A row whose
  object is not there, or is not the item, is dropped, as before: the item stays in OneDrive
  and the next reconcile places it in the folder again. Each such row is logged by its place
  in the folder and said in Activity (`restored`). What the row named outside is left as it
  is: nothing reaches it any more, so a placeholder that had not been downloaded yet stays
  outside the folder, marked and hollow, with no row to mark it again (it reads zeros once
  the helper restarts, Z3), and a downloaded file keeps its marks. Where `openat2` is not
  there (`ENOSYS`), no place can be looked at: nothing is renewed, the handles stay "not
  current", nothing is deleted on `ESTALE` and every `move-out` row waits (`stale-handle`),
  examination after examination, for as long as that lasts.
  Also: `local::handles::current_async`, which the move out asks before it believes an
  `ESTALE` (`upload/move_out/reach.rs`), only reads the record. With nothing recorded it
  answers "not current" and the row waits (`stale-handle`) until an examination has recorded
  the filesystem; it used to record it itself. Every row is made by an examination, which
  records first, so this is met only if that write failed. It is an async reading of the
  record beside the blocking `prepare` (quality finding `LO8`).
