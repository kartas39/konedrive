- **F261. After the folder's filesystem changed, a move out whose place leads through a
  symbolic link is given up, and the item comes back.** LIMIT (chosen), *measured*
  (`local::tests::liveness::on_a_changed_filesystem_a_place_reached_through_a_link_is_not_trusted`).
  Open. When the handles are taken again (`local::handles::prepare`; a new disk, a snapshot
  rolled back), a `move-out` row takes the handle of what stands where its object was last
  proved, if that carries the row's item id. The place is opened with no symbolic link
  anywhere in the path (`local::liveness::open_no_symlinks`), and the id, the inode and the
  handle are read from that one descriptor. A place that is reached only through a link (the
  directory it is in was replaced by a link to where it went) is therefore not found, though
  the object is there: the row is dropped, the item stays in OneDrive, and the next reconcile
  places it in the folder again, beside the user's copy outside. Before, the path was looked
  up three times by name with links followed, and such a row kept; whatever a link put there
  pointed at was taken for the object. Chosen: a path through a link is not a proof, and the
  cost is a file that is kept in OneDrive, never one that is deleted.
  Also: `local::handles::current_async`, which the move out asks before it believes an
  `ESTALE` (`upload/move_out/reach.rs`), only reads the record now. With nothing recorded it
  answers "not current" and the row waits (`stale-handle`) until an examination has recorded
  the filesystem; it used to record it itself. Every row is made by an examination, which
  records first, so this is met only if that write failed.
