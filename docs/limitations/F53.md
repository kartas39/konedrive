- **F53. A copy and a move are told apart by the file handle the store recorded**
  (`konedrived/src/local/examine.rs`) — (1) an item's inode (`items.local_handle`) is recorded when
  the reconcile places it, when a replacement swaps a new version in (`local::handles::record_replaced`), and
  whenever an examination finds the item. (2) An object carrying an item's id is the item only if
  the base places the item and the object is the recorded one (`Run::resolve`, the one place that
  decides it). When the recorded one is not among the objects the examination saw, or none is
  recorded (a rebuilt store, a filesystem whose handles were taken again), the object standing where
  the item is expected is taken: an editor's new inode that copied the attributes, a placement or a
  replacement whose record did not follow. While a row says the item was removed (its own `delete`
  or `move-out`, or one of a folder above it), that place is the base place: a folder deleted and
  restored there from a backup that kept the attributes is the item again, with what is in it, and
  the removal is taken back. Every other object carrying the id is a copy, the user's own, wherever
  the item's object is and without asking the helper: of an item the base does not place, of one
  whose object is elsewhere, gone or outside the folder. So a copy never renames or moves the item
  in OneDrive (issue #113). A copy that is not downloaded is a copy like any other, never the item,
  whatever became of the original. It is listed (`not-downloaded`). It is removed from the disk only
  when it holds no data and is certainly not the item (`Run::remove_empty`): the item's own recorded
  object was seen in the same examination. An id the store does not know at all is not such a case:
  it may be another account's (a file moved in from that account's folder, which its move-out still
  has to download where it went; `docs/design/writes.md` §8.3, F124), and the examination cannot ask
  whether another account claims it, so an empty object with an unknown id stays listed too, nothing
  unlinked. "The recorded object was not seen" is not "gone": an empty object may be the item's own
  file, moved where the examination did not look (while a copy at the old place was taken for the
  item), or, with nothing recorded after a rebuild, a file the user moved while the daemon was down;
  such a one stays listed, for good unless the user removes it. "Holds no data" is a regular file
  with one name in which `lseek(SEEK_DATA)` finds no data region, its state read as not downloaded
  through the same descriptor, under the lock a fill holds, its name checked against that descriptor
  right before the unlink; never the block count, which is not zero on ext4, where the marks alone
  take a block. A filesystem that does not report holes shows the whole file as data, and nothing is
  removed there. Between the last check and the unlink a program can still write into it: the window
  every removal has. The removal is said: a line in the journal and an activity event of the kind
  `removed` ("removed an empty copy of <name>: it held no content"), written to the store's log by
  the examination; it is not sent as a live signal, so an open window shows it when it next reads
  the log. One that holds any data, has another name, is being filled, or cannot be checked is never
  removed. So `cp -a a b; rm a` with `b` not downloaded (it comes from restoring a snapshot or a
  backup, hardly otherwise) deletes the item and leaves `b` listed (the item's object was gone, not
  seen, so `b` is not removed); the same when `a` went to the Trash. The user deleted the file, so
  it is deleted: its content is in OneDrive's recycle bin for 30 days, and restoring it there brings
  the item back. A `delete` of a folder recorded earlier waits for a `move` of an item out of it
  recorded later, whatever their order in the outbox (`konedrive-tree/src/outbox/pick.rs`, rule 3),
  unless the `delete` is already running. The price of the rule: with none recorded, what the user
  moved while the daemon was down is uploaded as new, and the item, which nothing proves deleted
  (F54), is placed again at its old place, so it exists twice — for a folder, the whole subtree: its
  downloaded files are uploaded as new under the new name, its files not downloaded are listed, and
  every item is placed again at the old path. A downloaded file copied with its attributes whose
  original was then deleted (`cp -a a b; rm a`) is a new file and a delete, not a rename, so the
  item's version history does not follow it; the same for an editor's save to a new inode that
  copied the attributes, followed by a `mv` in the same batch, before the new inode was recorded: a
  `delete` and a `create` with the content kept, where it was a `move` and an `update`. A copy
  standing at the item's place while the item's object is elsewhere and was not seen in the same
  batch is taken for the item, and the object that moved is then the copy: the same two files reach
  OneDrive, the new one under the other name. (3) Rename-to-a-backup saves (vim's `file~`) are
  recognised only when the backup's name is on the ignore list; under any other name the original is
  a move and the new file a create. (4) A copy, or a file from elsewhere (an item id the base does
  not know), is uploaded only if it is downloaded and has no other link; a placeholder cannot be
  read here (removed only as (2) says), and a file with other links (perhaps in another account's
  folder) would lose konedrive's attributes on every name, so both are listed instead. The marks
