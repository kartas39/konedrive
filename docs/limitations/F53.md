### F53. A move is told from a copy only by the recorded inode

- **Why:** Copies and backups can carry konedrive's attributes, so only the inode the store recorded
  proves which file is the item.
- **Effect:** After the store is rebuilt, a file moved while the daemon was down is uploaded as new
  and the item is placed again at its old place. A copy-then-delete, or a save by rename under an
  unknown backup name, becomes a new file and a delete, so version history does not follow. A copy
  that is not downloaded, or has other links, is listed and not uploaded.
- **Stays because:** Linux gives a file no identity that survives a copy except its inode, and
  guessing the other way could rename or delete the wrong item in OneDrive.
- **Where:** `crates/konedrived/src/local/examine/identity.rs`
- **Also:** The daemon removes an empty copy by name, because Linux cannot remove "this object and
  no other". A rename over that name between the last check and the removal makes it remove another
  file. The window is microseconds, and every removal by the daemon has it.
