- **F277. A placeholder that is in the way is removed, not rescued, also when it is being filled** (`folder/disk.rs`, `Disk::rescue`,
  `holds_nothing`; `remote/materialize/holding.rs`, `rescue`; quality finding `HY9`) — a file
  of ours that reads `online-only`, `hydrating` or `dehydrating` holds nothing made here, so
  `rescue` unlinks it in the folder and answers `None`, at the top as it already did inside a
  rescued directory. Before, such a file named itself was moved to the rescue directory and
  stripped of its state, where it read as a file of zeros of its full size; only the callers'
  own checks kept that from happening (one did not: an item's id on an entry of the wrong
  kind, read-only mode, `Materializer::place`). What that leaves:
  - **A fill or a free-up under way on the file is not waited for.** `rescue` does not take
    the per-inode lock. A fill then writes into a file with no name left, its opener reads
    what it downloaded, and the commit lands on the unlinked inode; a free-up empties it.
    Nothing of the user's is in such a file either way. The materializer's removals stop a
    download before they remove (`take_off`); `place` does not.
  - **`dehydrating` counts as holding nothing** although the file may still hold every
    byte: a free-up starts only on a file whose stamp matches, so OneDrive has what it holds.
  - **The rule is written twice**: `holds_nothing` here and the three states in
    `remote::materialize::holds_local_work` (`folder/` cannot use `remote/`).
