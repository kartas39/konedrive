- **F239. One path for every file's upload session: what a file of one fragment now does that was not measured against OneDrive**
  (`upload/content/session.rs` `Job::send_session`, `fragment`, `ended`, `stop_between_fragments`;
  quality finding `UP5`; the requests of an upload were measured for the shape before this
  change, F200). FRAGILE, *reasoned* (the first point: *measured* against the fake OneDrive,
  `upload::tests::sessions::a_session_resumed_after_the_item_changed_in_onedrive_never_overwrites_it`),
  open. A file with content goes up through one loop over the steps of a session (resume or
  open, fragment by fragment, ended), a file up to one fragment (10 MiB) as a session of one
  fragment. A file that goes up undisturbed sends the requests it sent before, in the same
  order. What is different for a file of one fragment, and for the rare answers:
  - **A session of one fragment that a later run resumes reads the item again before the
    fragment** (a changed file only: one more `GET /items/{id}`). `If-Match` is checked when a
    session is opened, not when it completes. Before this change a fragment refused for now,
    a network failure or a stop left the session in the row, and the next run sent the
    fragment with no look at the item: a version saved in OneDrive meanwhile was replaced by
    this one (it stayed in the item's version history, F80). Now that is a `412`, decided as
    any other. The item is not read again when the opening was the request just before. What
    stays unchecked is wider than one request, in two ways:
    - **A last fragment that is not taken is sent again with no new read of the item.**
      `DriveClient::upload_chunk` (`konedrive-graph/src/drive/upload.rs`) sends a fragment
      answered `429` or `503`, or whose answer was lost, again to the same session: up to 5
      sends in all, each after a wait of up to 300 s (`RetryPolicy`), about 20 minutes. A
      version saved in OneDrive in that time is replaced, as in the defect above. The same
      for every file's last fragment, and the same before this change; outside its files.
    - **Between the opening and a file's only fragment** the write gate is asked, the file is
      looked for under the row's names, its lock is taken, and up to 10 MiB are read. Before
      this change the read came before the opening, so this window was shorter.
  - **The stop is asked before the only fragment too.** A pause, the daemon's stop, a full
    OneDrive or a closed write gate that comes while the session is being opened leaves the
    row waiting with its session open and persisted; before, the fragment went out. The
    session's empty placeholder holds a new file's name in OneDrive for as long as the row
    waits, or until the session expires (the upload then starts over). The cost is one more
    asking of the write gate (one blocking section, one read of `config.toml`, F236) and one
    more look for the file under the row's names, for every file.
  - **A file removed, or replaced by another object under its name, while its session is
    being opened is not uploaded**: the session is cancelled and the row leaves with one
    `not-uploaded` event, and a replacement is queued as its own row (`removed`,
    `steps::never_uploaded`). Before, the old object's content went up and was committed as
    the object that was sent. During the fragment's own request nothing changed: it is
    committed as before.
  - **The session is opened before the file is read.** Before, a file of one fragment was
    read whole, and hashed, before the opening. A file that cannot be read in that moment (a
    writer since the run's first look, freed up, changed) now has a session: cancelled when
    it changed, kept when it is busy or not downloaded. A new file of one fragment that turns
    busy or not downloaded after its session opened keeps the session, and its placeholder
    holds the name in OneDrive until the row's next run completes it or the session expires.
    A `409`, `412` or
    `404` to the opening reads the file for its hash afterwards, once, as a larger file's did.
  - **An answer to a fragment that takes nothing of it** (`202` or `416` with the session
    standing where the fragment began, or before it) fails the row for now (`network`, in
    backoff) with its session kept, and the next run asks the session where it stands.
    Before, a file of one fragment sent it twice more and then failed the same way, and a
    larger file sent it again with no bound. What OneDrive answers in that state was not
    observed.
  - **A session found gone when it is resumed counts as the run's one start over.** A new
    session that then ends under its fragment (`404`) leaves the row in backoff (`the upload
    session ended twice`); before, a session found expired at the resume was not counted,
    and one more was opened in the same run.
  - **A session that expects bytes past the file's end** is cancelled and the row fails
    (`upload-error`, in backoff); the next run opens a new one. Not seen.
  - `Limits::small_max` and `konedrive_graph::drive::SMALL_UPLOAD_MAX` are gone: they were
    equal to the fragment's size, which is now the only boundary.

  Why: one loop in place of two that had drifted apart (the re-read of the item, the stop,
  the bound on a fragment that is not taken), so that each rule is written and tested once.
