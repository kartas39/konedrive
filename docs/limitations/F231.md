- **F231. The write gate and the hub's file calls run on blocking threads; the rest of `config.toml`'s readers do not**
  (`sync/hub.rs`, `sync/outbox_api.rs`, `config/mod.rs`; quality findings `SY8`, `CF1`, `X2`).
  FRAGILE, *reasoned*, open.
  - **The write gate is one blocking section** (`OutboxHost::may_write`, asked before each
    outbox row and between an upload's fragments). It reads `config.toml` again at every
    call, as before, so an edit by another process counts at the next row; nothing is
    cached. The section holds the gate's whole work: the reading, the folder's
    `outbox_note`, and the account's mode worked out again when the gate has just closed
    (which reads the file a second time). A section that has begun ends by itself. The
    worker is stopped by a token it looks at between its steps, never dropped at the gate,
    so only the runtime's own end can leave a section running with no worker to hear it.
  - **The worker now waits at the gate.** `may_start` and `gate_open` are `async`: other
    tasks of the same thread run between the question and the answer, where before the
    question was answered in one go, and the note and the mode are written from another
    thread than the worker's.
  - **`ConfigStore`'s lock is still a plain mutex held across the read**, so a call that only
    wants the last reading (`snapshot`, `account`, `client_id`) on a runtime thread waits
    for a gate that is reading on a blocking thread.
  - **Still on a runtime thread, with the file read and parsed there:** the account's mode
    (`recompute_mode` from a sign-in, a token refresh, a drive seen, a switch;
    `configured_mode`, `sign_in_mode`), `TokenExport.ReadWrite` (`writable_drive`), the
    switch to read-write (`writes_allowed`, and `current` under the session lock), the
    registration's `persisted_root_now`, and every write (`ConfigStore::update`: a read, a
    write and two `fsync`s). None of them is asked per outbox row. `CF1` and `AC6` have the
    rest.
  - **The hub's sections** (`route`: the item id of a moved-out object, the path check; a
    registration's overlap check; the device of a folder). Each begins and ends by itself
    and only reads. Left on the runtime thread: the `fstat` of the open descriptor
    (`InodeKey::of_fd`) and the `dup`s that give a section a descriptor of its own. The path
    check now needs one more descriptor than before for the time it runs.
  - **A registration has one more place to stop**: the folder's device is read on a blocking
    thread after `config.toml` records the folder and before the registration is kept in
    memory (`commit`, `abandon`, `hold`, `undo_switch`). A registration dropped there leaves
    what a daemon stopped at that point always left: the folder in `config.toml`, brought up
    at the next start.
  - **A panic in the path check or in the reading of a device is an answer of "not found"**,
    as the item id's read already was; a panic in the overlap check or in the gate is still
    the caller's panic.
  - **A section holds its account while it runs** (the gate's, the path check's candidates):
    an account let go meanwhile by everyone else ends on the blocking thread.
