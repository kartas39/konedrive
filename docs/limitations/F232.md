- **F232. A replacement's file calls run in three blocking sections, and a stop is heard only between them**
  (`remote/materialize/replace.rs`, `remote/listing/replacements.rs`; quality findings `RE5`,
  `X2`) — FRAGILE, *reasoned*, open.
  A replacement makes no file call on a runtime thread. Its calls are three sections on
  blocking threads: the check before the download (`check`), the new version made whole and
  put on the disk (`seal`, with the two `fsync`s), and the swap (`swap`). The download is
  between the first two; the waits for the tree lock and for the old file's lock are between
  the last two, as before. A section cannot be stopped once it has begun, so a replacement's
  worker is not dropped when its poller stops: the stop is handed down (`replace_until`) and
  ends only the waits — for the transfer pool, the download, the two locks. What that leaves:
  - **Nothing makes a caller wait for a section.** `Poller::stop` returns when no replacement
    is at work only because the workers are not dropped. Code that drops a replacement's
    future (a `select!`, a timeout, an abort) leaves the section under way on its thread,
    with a `Disk` and, in read-write mode, a `Store` of its own: it can open a locked
    directory's write window, rename, and call the store after its caller is gone. The swap
    keeps the tree lock and the old file's lock until it ends, which keeps off only what
    takes them. The guard is moved into the section whole and not shared as a fill's is
    (`InodeHold`, F230): a replacement does nothing beside its section.
    If the future of `Poller::stop` is itself dropped while it waits in `join_replacements`,
    the workers go on and stay on record (`Replacements::join` puts back the one it was
    waiting for): nothing is aborted, and the next `join_replacements` waits for them. But
    nobody waits meanwhile, so a section can still be under way after that dropped stop.
  - **A stop waits for what it used to drop, in both modes.** Before, a stop dropped the
    replacement wherever it waited. Now it waits for:
    - the opening of the root (`Disk::open`, a blocking hop in `replace_through`);
    - the store's answer to `land_deferred`, in read-write mode, which the swap asks for
      from its section (`call_blocking`) under the write lease: the lease borrows the old
      file and so cannot be handed back;
    - the store's answer to `record_replaced_async` (`set_local_handle`), in both modes.

    At the two store calls the call was already sent when the replacement was dropped, and
    the replacement was not said; now it is in the activity log. A stop waited for a run of
    file calls under way before as well.
  - **A stop heard after `check` or `seal`** ends the replacement where a stop during the
    download or during a wait for a lock ended it before: the nameless file is closed and
    gone, and no lock is held.
  - **A section waits for a blocking thread**, the swap with both locks held. The pool has
    512 threads, and a folder runs at most `REPLACE_WORKERS` (8) replacements at once.
  - **A section the runtime does not run** (it is shutting down) fails the replacement with
    "the replacement task failed"; a panic in a section is the replacement's own panic, as
    before.
  - Nothing of `replace_inner` is left on the runtime thread. `replace_through`
    (`remote/listing/replacements.rs`) is outside this change: `record_replaced_async` still
    opens the directory and reads an attribute and a file handle there.
