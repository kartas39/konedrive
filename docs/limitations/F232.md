- **F232. A replacement's file calls run in three blocking sections, and a section that has begun ends by itself**
  (`remote/materialize/replace.rs`; quality findings `RE5`, `X2`) — FRAGILE, *reasoned*, open.
  A replacement makes no file call on a runtime thread. Its calls are three sections on
  blocking threads: the check before the download (`check`), the new version made whole and
  put on the disk (`seal`, with the two `fsync`s), and the swap (`swap`). The download is
  between the first two; the waits for the tree lock and for the old file's lock are between
  the last two, as before. A section cannot be stopped once it has begun. A replacement is
  dropped only when its poller stops (`Poller::stop`). What that leaves:
  - **A swap left behind ends without its replacement.** Before, a replacement could be
    dropped while it waited for a lock or, in read-write mode, for the store after the
    rename, and nowhere between. Now it can be dropped anywhere in the swap; the section
    goes on to its end and the rename happens, with nobody to hear of it: no line in the
    activity log, and no call of `record_replaced_async`. In read-write mode the section
    records the new inode itself (`land_deferred`), so nothing is missing. In read-only mode
    `items.local_handle` keeps the old inode until an examination sees the file
    (`local/examine/found.rs`, `SetHandle`); before, this needed a drop while the store's
    queue was full.
  - **The swap keeps its locks, not its poller.** The tree lock (read-write mode) and the old
    file's lock go into the section and are let go of when it ends. The lock is moved in
    whole and not shared as a fill's is (`InodeHold`, F230): a replacement does nothing
    beside its section. `Poller::stop` waits for the replacements' tasks, not for a section
    left behind: what follows a stop and takes neither lock (in read-only mode there is no
    tree lock) can run beside the end of a swap. A lock or unlock of the whole tree
    (`Disk::lock_tree`, `unlock_tree`) meets it at the directory's write window, as F14 says
    of a reconcile.
  - **The store call after the rename is made from the section** (`call_blocking`), under the
    write lease, which borrows the old file and so cannot be handed back to the replacement. Before, the call was sent and
    the replacement waited for it; dropped there, it let go of the lease and the locks before
    the store had answered, and a failure of the call was not logged. Now the lease and the
    locks stay until the answer, and a failure is logged (`warn`) though the replacement is
    gone.
  - **A check or a seal left behind** changes nothing a user sees: the nameless file is closed
    and gone. The check's write lease (taken and let go of at once) and its write window on a
    locked directory (for the nameless file) end as they would have.
  - **A section waits for a blocking thread**, the swap with both locks held. The pool has
    512 threads, and a folder runs at most `REPLACE_WORKERS` (8) replacements at once.
  - **A section the runtime does not run** (it is shutting down) fails the replacement with
    "the replacement task failed"; a panic in a section is the replacement's own panic, as
    before.
  - **`Disk` is cloned into each section**: the clones share the root's descriptor
    (`Arc<File>`), so a section left behind keeps the root open until it ends.
  - Nothing of `replace_inner` is left on the runtime thread. `replace_through`
    (`remote/listing/replacements.rs`) is outside this change: `record_replaced_async` still
    opens the directory and reads an attribute and a file handle there.
