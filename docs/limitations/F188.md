- **F188. A folder that can no longer be placed stays on disk while anything in it waits**
  (`konedrived/src/remote/materialize/removal.rs` `take_off`, policy `Unplaced`, `waits`, `differs`;
  `remote/materialize/rw/unplaced.rs` `after_placement`, `wait_to_leave`; `konedrive-tree/src/reconcile.rs` table `deferred`;
  write design §9 "What can no longer be placed"; issue #104) — an item OneDrive still has and this
  folder cannot hold (a name too long, a reserved name, the Personal Vault, shared, OneNote,
  unsupported, or a folder above it that is one of these) leaves the disk whole, in the cycle that
  learns of it, when nothing in it waits. While anything does, nothing of it is touched: the base
  keeps it placed where the disk has it, with its recorded object, OneDrive's row of it waits in
  `deferred`, and it is an item like any other. Until schema 7 it had a state of its own (`leaving`);
  that is gone (F256).
  - **What waits** is listed in write design §9. It is what the cycle finds by walking the directory
    and the base side by side, not what an examination would record: it does not hash, so a download
    rewritten with the same content and a new time waits for the examination that then records
    nothing, and goes a cycle later.
  - **It can wait for ever.** A blocked row, a file whose state cannot be read, a file from elsewhere
    that is not downloaded, a file or a non-empty directory under an ignored name, and another
    filesystem mounted inside keep it until the user does something. The line in `Skipped()` says
    which, with a path (F257).
  - **While it waits, every poll runs a cycle**, which walks the folder that waits once: a `stat`
    and the attributes of each object in it, and one store query for each directory.
  - **What OneDrive adds inside it does not appear here**, and what OneDrive moves out of it or
    removes inside it is carried out in a cycle that names the item (a Changed one); a Full reconcile
    leaves everything below a folder that waits as it is.
  - **The look right before each unlink** stops a removal that meets local work made since the walk.
    What went before it is gone (files not downloaded, downloads unchanged), the objects are
    forgotten, and what is left stays an item: an examination records it again where it stands, and
    proves nothing gone. Between that look and the unlink a program can still open the file for
    writing: the window every removal has.
  - **What cannot be looked at waits or fails, and is never taken for absent.** An item no longer
    placed whose object is not on disk and has no record is taken by the base at once, but only
    when its folder could be opened, or is gone (`ENOENT`, `ENOTDIR`); with any other error its
    change waits. Inside the folder, an error while a directory is listed or an object is probed
    fails the cycle (F194). A base item with no object on record that a listing does not show is
    taken for absent: nothing could prove otherwise.
  - **Only what was looked at is removed.** An object that carries an id the look did not find (a
    placed file moved in since) stops the removal, as local work does, and so does a directory
    that is not empty by then. After a removal that stopped, whatever stopped it, or failed, the
    place is handed to the examination, which records again what the store had forgotten.
  - **It yields its name.** When another item takes the name of one that can no longer be placed
    (in the same listing, or while it waits), the one that can no longer be placed steps aside: it
    is renamed where it is to the copy name (`name-<machine>.ext`, the first free one), with its
    attributes, and the base takes that name in the same store transaction as the rows that name
    it. The base and the disk agree, so nothing is sent for it; it leaves from there in the same
    cycle if nothing in it waits, and its skipped line says where it is ("It is at …"). Always
    this side yields, so nothing waits for a name that waits for it. A rename the user then makes
    of it is the user's and is sent; a change of its content goes into the item with no name.
  - **A stop of the daemon between that rename and its record** leaves the object under the copy
    name and the base at the old one, and the scan at the next start records a rename. The next
    reconcile that looks at the item (the first cycle after a start is a Full one) knows the name
    for its own — the item can no longer be placed, and stands beside its base place under one of
    the copy names of it (one function for both scopes; in a Full reconcile only when no other
    object carries the id) — takes it into the base and drops that row before the worker sends
    it. A user who renames a waiting item to exactly its own copy name gets the same: the rename
    is not sent.
  - **The folder goes after what OneDrive moved out of it is placed.** A child still in the holding
    directory by then (the name it has in OneDrive is held here by something a local change made,
    which does not yield) keeps the folder for as long as that name is held. It is put back into
    its own folder — the directory that carries the folder's id, wherever it stands by then, under
    the name the base has for the child — never into whatever stands at the path it was taken
    from, which may be a newcomer's. The folder's line names the child where it is, and says that
    its name is taken (`moved-in-onedrive`). The child's own change waits too and has no line of
    its own: it is not a skipped item. While its new name is held it is not taken to the holding
    directory at all: an item whose place in the new tree is held by a local change is left where
    it is, with what is below it, and nothing of it is touched until the name is free.
  - **Rows follow a folder the reconcile moves.** The outbox rows below a folder are re-based to
    its path in the holding directory when it is taken there, and from that path to where it is
    placed or put back: each row is re-based once, by the folder that carried it, so two folders
    that exchange names do not take each other's rows. A step aside re-bases the item's own rows
    by its id. While a cycle runs, such rows name a path in the holding directory; a cycle that
    stops there leaves them so until the next Full reconcile drains it. Before, rows below a
    folder renamed in OneDrive kept the old path until an examination met their files.
  - **A chain of names that hangs on a local change waits whole.** An item whose new place is
    taken by another item that is itself to move, whose own new place is held (and so on), is
    left where it is; nothing of the chain is moved until the change that holds its end is sent.
    Names that only go round (an exchange) hang on nothing and are exchanged at once. The items
    of a chain that wait are placed items with a move deferred: they have no line on the skipped
    list.
  - **What is put back under a copy name** (its own name was taken while it was in the holding
    directory) takes the base along to that name, as a step aside does: no rename is recorded
    for it. Its move still waits.
  - **An item that is itself a mount point cannot step aside** (`EBUSY`): it keeps its name and
    waits, shown as `mounted-inside`, and what takes its name waits for it, with no line of its
    own. Not tried: a test cannot mount.
  - **A take-off acts on the object, not on a path remembered.** Where the item stands is asked
    when it is taken off: the name it stepped aside to, or the name the base has in the directory
    that carries its folder's id, which the same run may have moved. The object there must carry
    the item's id; anything else is not touched, and the item waits for the next cycle.
  - **An item whose folder cannot be opened** for another reason than being gone is said as "cannot
    be read" (`unknown-state`).
  - **A Full reconcile** moves what OneDrive moved out of such a folder before it takes the folder
    off, and leaves everything else below a folder that waits as it is: an item OneDrive removed
    inside it stays until a cycle that names it (a Changed one).
  - **A file that is not downloaded and is not where the base has its item** (a copy, a file from
    elsewhere, or what the step to schema 8 left, F256) keeps the folder until the user moves it
    out; the line says so, and does not advise deleting it, since the same line stands for a placed
    file's placeholder just moved in, whose delete would be sent. A rename the user made of such a
    file is recorded by the examination: every cycle hands each such file over by its name (a look
    at one name, not at the folder), and the rename then waits as an upload.
  - **A file with other names** (hard links the user made): its own name goes, and the id is then
    taken off the inode (F238); the other names are the user's own files.
  - **A rename of the waiting item itself, made here, wins.** It is sent, and the item gets the
    user's name in OneDrive in place of the one the folder could not hold.
