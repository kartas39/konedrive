- **F197. A `403` blocks only its row, and the row is tried again whenever a worker begins**
  (`upload/engine/drain.rs` `settle`, `upload/engine.rs` `release_forbidden`; quality finding
  `UP1`) — the worker cannot tell a `403` about one item (a folder shared read-only, a file the
  service holds) from one about the whole sign-in, so it blocks the row (`forbidden`) and goes on.
  What follows:
  - If OneDrive answers `403` to everything, every row is sent once and blocked, each with its
    own `upload-failed` event, instead of the account stopping at the first. Each event also
    raises a desktop notification, which the notifier joins into one for those inside its
    window (`app/tests/notifiertest.cpp`).
  - The blocked rows are made `ready` by every worker, at the first look at which it may send,
    not only after a sign-in: a restart or a switch to read-write sends each of them once more,
    and a row OneDrive still refuses is blocked again. No second event is written only while
    the row's reason is still `forbidden` when it is taken; a released row that first ends
    another way (a backoff, a wait) has another reason by then, and a later `403` writes the
    event, and notifies, again.
  - `LastError` does not mention a `403`: the row's reason in Not Uploaded does.
  - The Sign In Again action Not Uploaded shows for these rows starts a sign-in only while the
    account is signed out (`account/sign_in.rs`: `BeginSignIn` answers `Busy` otherwise). An
    account that is signed in has to sign out first; a sign-in is not what releases the rows of
    a `403` about one item anyway.

  Why: a sign-in always starts a new worker, and nothing else tells the worker that one
  happened; one request for each blocked row at a start is cheap beside stopping every upload of
  the account for one item. DESIGN · measured
  (`upload::tests::candidates::a_row_blocked_by_403_goes_again_with_the_worker_a_sign_in_builds`,
  `a_row_blocked_by_403_stays_blocked_while_the_new_worker_may_not_send`) · open.
