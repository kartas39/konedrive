- **F197. A `403` blocks only its row, and the row is tried again whenever a worker begins**
  (`upload/engine/drain.rs` `settle`, `upload/engine.rs` `release_forbidden`; quality finding
  `UP1`) — the worker cannot tell a `403` about one item (a folder shared read-only, a file the
  service holds) from one about the whole sign-in, so it blocks the row (`forbidden`) and goes on.
  Two things follow. If OneDrive answers `403` to everything, every row is sent once and blocked,
  each with its own `upload-failed` event, instead of the account stopping at the first. And the
  blocked rows are made `ready` at every worker's beginning, not only after a sign-in: a restart
  or a switch to read-write sends each of them once more, and a row OneDrive still refuses is
  blocked again (with no second event). `LastError` does not mention a `403`: the row's reason in
  Not Uploaded does. Why: a sign-in always starts a new worker, and nothing else tells the worker
  that one happened; one request for each blocked row at a start is cheap beside stopping every
  upload of the account for one item. DESIGN · measured
