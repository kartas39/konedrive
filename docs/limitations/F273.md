- **F273. The daemon exits when a task it needs is gone, and counts on systemd to start it again**
  (`main.rs`, `daemon/stop.rs` `Tasks`; quality finding `SY11`). FRAGILE, *reasoned* (the rule
  that names a task that is gone has a test; the exit itself runs only in `main`, which no test
  starts), open. `main` keeps the four tasks it starts beside the accounts. The end of the
  helper's supervisor or of the watch of the helper's state, however it ended, and a panic of
  either watcher of `conditions`, stops the daemon as a signal does (the outboxes are closed,
  within the bound of F177) and the process exits with 1. Before, the daemon stayed up, said
  ready and filled nothing. What that leaves:
  - **Who starts it again.** The unit says `Restart=on-failure`
    (`packaging/systemd/konedrived.service`). A daemon started by hand, or by D-Bus activation
    outside systemd, stays down until the next call activates it.
  - **A failure that comes back at every start restarts the daemon for ever, every few
    seconds.** The unit waits 5 s before a restart (`RestartSec=5`), so systemd's start limit
    (by default five starts in ten seconds) is never reached and the unit never ends as
    `failed`. Each round brings every folder up again, and a round that had uploads in flight
    cuts them after the stop's ten seconds. Nothing counts the rounds or gives up.
  - **One account's defect is kept from the tasks that serve every account** (`sync/registry.rs`).
    The supervisor brings every account's folder up on its own task as the helper connects: a
    panic in one account's bring-up is caught there, that folder is left down with a `LastError`
    that says so ("failed inside konedrive"), and the next account is brought up. `Refresh()`,
    the next connect or the next start tries it again; its registration at the helper is left
    as the panic left it. What every account is told from those tasks (the helper's state, its
    loss, the hold's settings, a network that is back) is caught for each account too, and
    only written to the journal. So what still ends the daemon this way is a panic in the
    supervisor's or a watcher's own code, not in an account's.
  - **A panic inside a change of a folder leaves the folder's state as the change had it at
    that moment**, published as the change is dropped; the catch then puts the folder down
    from whatever is there. If that panics too, the folder stays as it is, with a line in the
    journal.
  - **A watcher of `conditions` that returns is not a failure.** With no system bus, no
    NetworkManager or a source whose signals ended, it says so in the journal and ends, as
    before; the daemon goes on without it and nothing starts it again: the hold stays as it was
    last worked out, and a lost network is noticed by retrying.
  - **Not kept:** the task that announces `Accounts.HelperState` (`dbus/signals.rs`; it ends
    only with the process, D50), each account's signal tasks (the account manager's, stopped when the
    account is removed), and everything a folder's sync runs. A panic in one of those still
    ends that task alone.
  - **The stop at such an end waits as any stop does**: up to ten seconds for the uploads in
    flight, and a signal meanwhile ends it at once.
