- **D42. What the running sync as an object leaves by hand.**
  DEBT · reasoned (part 4 of `B5`, quality finding `SY3`). A OneDrive folder's sync is one object
  in the folder's state (`sync/running_sync.rs`: `RunningSync`, inside `Content::OneDrive` of a
  folder that is up), its parts are linked to each other when they are built, and it stops by
  being dropped. What the types still do not say:
  - **A drop cannot wait.** A dropped `RunningSync` tells every part to stop and hands the parts
    to the service (`Ended`); `SyncService::change` waits for them, under the state lock, before
    it gives out a `Stopped`. So the rule "a section that has begun runs to its end before the
    folder is changed" (`F233`) holds for every change, also after one that was cut, but it holds
    because `change` is the only door, not because a part cannot be dropped elsewhere. A service
    that is itself dropped waits for nothing: its parts are told, and end on their own.
  - **A sync a cut change stopped stays stopped until the next change.** A change tells the sync
    to stop and takes it out of the view before it waits for the state lock, so from that moment
    no reader takes it for running, and `Refresh()` goes through a change. Cut before the lock,
    the sync is still in the state, told and not waited for; cut after, the state says
    `Why::Interrupted` and the change publishes that as it is dropped. Either way the next change
    of the folder takes it out, waits for its parts and starts another (`Refresh()`, the helper
    back, a switch of mode); nothing does on a timer. A sync that was told to stop reads as not
    running whatever the view was made from (`Handles::told_to_stop`). Between a cut before the
    lock and that next change the bus shows what it showed, except `Writable`, which is false.
  - **The tree store, the content source and the tree lock are kept with the folder's record**
    (`Record.kept`), up or down: the store is opened when the folder's sync first starts, or
    when a change first needs it, and closed only when the folder is forgotten, its account
    removed, or another folder registered. So a folder that is down still fills an open, still
    says its pause and what waits to be uploaded, and its tree still claims its items for the
    other accounts, as before. That there is one connection to the store is one function
    (`kept_store`). That the store is closed before its files are removed is kept by hand: the
    record a reader gets carries nothing kept (`Record::bare`, made by `publish` and by the two
    readers that take the record from the state), a download holds the source alone, and a
    Forget waits, at most ten seconds, until every connection is closed (`Store::close`) before
    it removes the files. A new holder of a store clone that outlives a Forget makes that wait
    run out, and the files go all the same, with a warning.
  - **A watcher that ends by itself is not started again on its own.** The folder's sync is
    started again locked and says why (`OneDriveFolder.watcher_ended`), until the folder is
    brought up again or its mode is switched. It is said once, and only of the sync the
    watcher belonged to (the sync's number).
  - **One task publishes without a `Stopped`:** for a root that is unlocked already (a daemon
    start), the sync's own task says when the watcher's walk is over, with the state held for
    reading, so that the bring-up does not wait for the walk. It writes one shared cell of the
    running sync (`Lock`), nothing else.
  - **Why a sync could not start is in the state (`Why::CannotStart`), and is shown through the
    snapshot's `sync_trouble`**, which a running sync's cycles write too: `publish` writes the
    one, the cycle the other, and the first cycle that succeeds clears whichever is there.
  - **`remote::listing::Writes` still takes closures.** They hold the handles of the same sync's
    watcher and worker and nothing of the service, but the type does not say so; `remote/` cannot
    name `upload/`'s handle (the layer order).
  - **Two links still go through the service, by a weak reference:** the watcher's status hook
    (the folder moved or deleted takes the folder down, which only the service can) and the
    pins' downloads. The routing of moved-out item ids knows an account by its id
    (`sync/registry.rs`, part 5).
  - **The readers of the bus read the folder's tree store from the view, with no state lock**
    (`Changes()`, `NotUploaded*`, `Pause`, the free-up's check): a Forget does not wait for one of
    them, as before. `Skipped()`, the count before a switch to read-only and the registry's router take
    the store from the state, under the lock.
  - **The pins' sweep of a local folder that came up is still a detached task** (`bring_up.rs`
    `run`): nothing owns it or waits for it.
  - **`Folder.Writable` is false while a read-write folder's sync starts** (`Lock::Walking`: until
    its watcher has walked the folder and the lock is off), and from the moment a change tells
    the sync to stop, so a client that reads it then shows "read-only for now"; it turns true
    with a `PropertiesChanged`.
  - **Four tests seed outbox rows through the test support** (`sync::testing::tree_store`: a
    blocked row, a held delete) instead of producing them by changing files; `stop_sync` of the
    test support stops a sync through `change`, and leaves it stopped.
