- **F293. Three crash windows of a rescue, a conflict copy and a removal that keeps something stay open**
  (`konedrived/src/remote/materialize/rw.rs` `copy_aside`; `remote/materialize/removal.rs`
  `stays`; `folder/disk.rs` `outside`; `remote/materialize.rs` `place`; quality finding
  `UP7`) — since the item id goes first (`F292`), a crash in the middle of a strip no longer
  leaves an id with no state. What is still open, none of it losing a byte:
  - **A file whose state does not say "downloaded" can reach the strip of a conflict copy.**
    `placeholder::strip` is only for an object whose content is there. A rescue keeps to
    that (`Disk::rescue` and `outside` remove a file that is `online-only`, or between two
    states, instead of stripping it), and so does a removal (`stays` keeps only a download
    or a file with no readable state that holds data). `copy_aside` does not look: a file
    that carries the id of an item which is a folder in OneDrive (`place`, "its own id with
    the wrong kind"; nothing konedrive or Graph makes) is copied aside whatever its state. If
    it was not downloaded, the copy ends as a file of zeros of the user's own, uploaded as
    new: so before this change too. A crash after the id is gone now leaves it with a state
    "not downloaded" and no id, which the helper does not let through as an ordinary file
    (it asks for a fill; what the daemon answers for a file with no id was not run);
    before, the crash could leave that or an id with no state.
  - **A state that is no value konedrive writes** (or cannot be read) on a file that holds
    data: the helper refuses the file with or without its id. A crash after the id is gone
    leaves the refused state on a file nothing takes it off again, since without an id it
    is the user's own; before, the listing order decided which of the two was left. Such a
    state is not written by konedrive.
  - **The rename comes before the strip.** A crash between them leaves the object under its
    copy name, or in the rescue directory, with every attribute: inside the folder the next
    reconcile finds an item of its own at a name the tree does not have; outside it nothing
    looks again, and the marks stay on what was rescued. The order of the strip does not
    change this.

  Also not looked into: whether the next reconcile settles each of these leftovers was not
  run, only read.
