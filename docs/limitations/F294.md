- **F294. Once an account is read-write, nothing but the user's own switch stands between a change in its folder and the user's real OneDrive**
  (`konedrived/src/account/mode.rs`, `switch_to_read_write`; `sync/mode.rs`, `Gate::refusal`;
  write design §2.2, §2.3) — uploading is the user's choice for any signed-in account: the
  switch on the Account page, or `konedrivectl account mode read-write`, with its sign-in in the
  browser for `Files.ReadWrite`. No list of test accounts decides it any more (F60). After that
  sign-in, every change in the folder that the examination takes for the user's — an edit, a
  rename, a move, a delete, by any program, script or stray command — is sent to the account's
  OneDrive within seconds. What still stands in between is what the upload design has for every
  account, not a second consent: the write gate's own conditions (F60), the guards on each
  request (`If-Match`, `conflictBehavior=fail`), conflict copies, the mass-delete guard, and
  OneDrive's recycle bin and version history. A defect in the upload path now reaches real
  files, where before it could reach only a test account's. The way back is the same switch:
  read-only stops the uploads at once (changes waiting are kept, or dropped when forced, F140).
  A hand edit of `mode` in `config.toml` is not enough to upload by itself: the token must have
  been granted `Files.ReadWrite` in a sign-in, and reach the recorded drive (F61). An account
  whose `config.toml` already says `mode = "read-write"` — set while its drive was on the list,
  or by hand — runs read-write with this version as soon as its token grants it, with no new
  switch; its next sign-in asks for `Files.ReadWrite`. LIMIT, on
