- **F245. The base records a local object only for an item it places: where the store keeps
  that, and where it does not** (`konedrive-tree/src/forget.rs` `forget_unplaced`,
  `forget_all_unplaced`; `staging.rs` `swap`, `apply`, `turns_placed`; `outbox.rs` `outbox_commit`) —
  whatever writes a row into `items` that the base then does not place (the row itself, or a folder
  above it) clears its recorded object and those of everything below it, in the same transaction:
  a cycle's swap, a page of a first listing, a deferred change applied or landed, an outbox commit.
  Before, the swap kept the object of a row that turned not placed, and the daemon had to have
  forgotten it first. What this does not cover:
  - **The setters are not guarded.** `set_local_handle`, `set_local_handles` and
    `OutboxOp::SetHandle` write what they are given, into `items` and `staging`
    (`outbox_commit_temporary` keeps the rule since `B4-6`, as `outbox_commit` does). A cycle that places
    a row which turns placed records its object in `items` before its swap; if the cycle fails
    there, the row keeps an object while the base does not place it yet. So the forgetting of a row
    that turns placed (`turns_placed`, F189) stays, and is what keeps such a leftover from being
    taken for the item's object by the next cycle.
  - **An installed store is swept once**, by the step to schema 8: every row the base does not
    place loses its recorded object (F256).
  - **A move out of a folder that OneDrive moved below a folder that is not placed.** The items
    the base has inside it are no longer placed and lose their recorded objects at that cycle's
    swap. If one of them is not found in the folder where it was moved to, the move out cannot ask
    after it by its handle (`upload/move_out/cases.rs` `left_since`) and waits, shown among what is
    not uploaded; nothing is deleted in OneDrive. Before, it could be asked after. Not reproduced.
  - **Dropping a row forgets by leftover staging too.** `outbox_drop` and `outbox_drop_held`
    forget what the new tree has below the item, and `staging` may be what a cycle that failed
    left. An item staged below the folder then loses its object while it is still elsewhere in the
    folder. The next cycle finds it by its id where the base has it. If the user also moved it and
    no examination saw the move yet, nothing ties the object to the item any more: it is not at the
    item's place and not recorded, so the examination takes it for a copy and uploads it as new,
    and the item is placed again: two files, nothing lost. Reasoned, not reproduced.
  - **A delta's swap asks a point query for each row it wrote**, and one more for each folder
    above them that was not asked yet. In the daemon's bench (a debug build, one run of each) a
    delta of 30 000 rows over a store of 100 000 took 6.2 s read-only and 9.9 s read-write, against
    8.4 s and 8.4 s before: no difference that one run shows.
