- **F198. The order of the tree lock and the folder's state lock is kept by hand on the cycle's side** —
  the rule (the write design §9): only a cycle holds the tree lock while it waits for the folder's
  state lock (the lifecycle lock of the write design), and only a writer of the state lock that has
  stopped the folder's sync takes the tree lock under it. The writer's half is in the types now:
  the folder's state is inside the lock, the only way to change it is `SyncService::change`, which
  stops the sync first, and the `Stopped` it gives is the only thing that hands out the tree lock
  under the state lock (`sync/folder.rs`). The reader's half is not: a new caller that takes the
  state lock as a reader and then the tree lock, or the tree lock and then the state lock without
  being stopped with the poller, brings back the hang of three (a cycle or the watcher's
  examination, that caller, and a writer waiting for the state lock). `RestoreDeletes` takes the
  tree lock with no state lock, which is safe only as long as it takes no state lock under it. One
  edge is easy to miss: stopping the sync waits for the examination under way, which holds the tree
  lock. One test covers the forced switch (`sync::tests::onedrive::read_write`, the cycle, the
  forced switch and the bring-up at once); the rest is argued from the code. What the user can see
  of the fix: a forced switch to read-only answers only once the folder's sync has stopped, the
  lock walk has run and a read-only sync has started — the work the folder's turn did just after
  the answer before — so `SetMode` takes that much longer on a large folder; and for the moment
  between the drop and the account's own mode being worked out again, the folder is read-only
  while the account still says read-write. FRAGILE. Reasoned. Open.
