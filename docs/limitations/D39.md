- **D39. An upload's answer that the folder cannot hold waits only when the item's own row says
  so** (`konedrive-tree/src/outbox.rs` `outbox_commit`) — when OneDrive answers an upload with the
  item under a name or of a kind the folder cannot hold (renamed there to a name over 255 bytes
  while the content went up), the commit leaves a placed item where the disk has it, with the new
  version and its object, and stores the answer as the item's deferred change; the next cycle takes
  the item off the disk. Before, the base took the answer: the item was not placed, its file stayed
  with its id, and an examination took it for a copy and uploaded it again as new (reasoned from
  `local/examine/classify.rs`, not reproduced). Left as it was:
  - **An answer whose folder is not placed** (the item moved in OneDrive into the Personal Vault
    while its content went up) still becomes the base's row, and loses its object (F245). The store
    cannot tell it from a move the user made into a folder that is leaving (#104), whose answer
    names that folder too. It can be told once the leaving rows are gone (`B4`, part 6).
  - **The worker is not changed.** A `412` for a rename made in OneDrive to a name the folder
    cannot hold still ends with the local name sent back (`upload/content.rs` `Job::changed`,
    `follow_cloud`), so the rule is reached by an upload guarded by a cTag alone, and by a rename
    that lands in OneDrive after the guard was checked: during a long upload session, whose last
    fragment's answer then names the item as it is now (reasoned, not tried). Part 6 sends no name
    and no parent for an item that waits.
  - `outbox_drop` still takes a base row to write, which no caller gives.
