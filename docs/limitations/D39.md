- **D39. An item OneDrive moved where the folder cannot hold it: what the upload worker knows, and
  when** (`konedrived/src/upload/content.rs` `Job::changed`, `unmoved_here`; `upload/steps/shared.rs`
  `holds`; `konedrive-tree/src/outbox.rs` `outbox_commit`, `would_place`) — a change of content is
  recorded against the place the base has. When OneDrive has renamed or moved the item meanwhile to
  where the folder cannot hold it (a name over 255 bytes, a folder that is not placed here such as
  the Personal Vault), the worker sends no name and no folder back: the content goes into the item
  where it is, the commit keeps the base's place and takes the version, and the answer waits as the
  item's deferred change (F188). What that rests on, and what it costs:
  - **The worker learns it from a `412`**, each time: the row keeps the tag and the place it was
    recorded with, so every attempt that follows a failure meets the `412` again, reads the item
    and sends the content with the tag just read. One request more for each attempt.
  - **"Nobody moved it here"** is read from `items` without the tree lock: the object's folder and
    name are the base's. A move the user made is sent, so a rename made here and a rename made in
    OneDrive to a name the folder cannot hold end with the user's name (F188).
  - **A folder OneDrive moved the item into that this computer has not heard of yet** reads as one
    the folder cannot hold: the content goes into the item there, the commit keeps the base's place,
    and the next cycle moves the file to that folder once it is placed. Before, the item was moved
    back in OneDrive.
  - **A move that lands in OneDrive after the guard was checked** (during a long upload session,
    whose last fragment's answer names the item as it is by then) is caught only by the commit,
    which keeps the place for an answer the base would not place.
  - **A commit that keeps the place writes the place the disk has after the row**: the folder and
    the name the row took the item to where the user changed them, the base's otherwise, with the
    answer's version; so do the rows behind it and the move a temporary step leaves
    (`local_place`, `outbox_commit_temporary`). OneDrive's place is in the deferred change alone.
    The folder is the one the row names: a row recorded before its folder was made in OneDrive
    names none, and the worker writes the folder it finds into the row before it sends anything
    (`parent_recorded`), so the commit and a replay after a stop know it.
  - **A rename or a move the user made** is sent, and only that: after a `412` for an item that
    OneDrive has where the folder cannot hold it, the row's base takes OneDrive's side for the
    field the user changed and keeps the row's own for the other (`base_after_a_change`), so a
    rename made here does not also move the item back out of the Personal Vault, and a move made
    here does not also rename it back. Where the folder can hold OneDrive's place, a rename made on
    both sides is settled as before (write design §6).
