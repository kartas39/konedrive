- **F235. A delete that follows a read of the item goes out with an empty `If-Match` when the answer carried neither tag**
  (`upload/steps/shared.rs` `Guard::of_item`; its callers in `steps/shared.rs`, `steps/meta.rs`
  and `upload/content.rs`; quality finding `UP9`; F200 for the bad item). FRAGILE, *reasoned*,
  open. A request made against the version a row's change was made from has a guard or is not
  sent: with neither an eTag nor a cTag in its base the row is blocked (`no-guard`,
  `Guard::of_base`). A delete of an item that was just read, or just answered, takes its guard
  from that answer instead, the eTag or else the cTag, and is sent even when the answer has
  neither: the header is then `If-Match:` with no value. This was so before the guard was
  written in one place; it is kept, for a decision.
  - **When**: only when OneDrive answers a read, or an upload, with an item that has neither
    `eTag` nor `cTag`. The reads (`DriveClient::item`, `child`) select no fields, so the tags
    are left out only if OneDrive leaves them out. Not seen; the fake always gives both.
  - **What OneDrive answers to an empty `If-Match` was not measured.** The three answers that
    can be told apart here are success (the delete is then unguarded), `412` and `400`.
  - **Where, and what each answer does**:
    - `landed_away` (a `create` whose file is gone, and whose last request may have made the
      item): success deletes the item whatever happened to it since the look-up; `412` leaves
      it in OneDrive as someone else's, and the next cycle places it here; `400` blocks the
      row (`refused`), which has no file any more.
    - `clear_bad_item` (the item a bad upload made, before the file goes again): reached with
      no guard only when no tag is remembered either (a row an older version wrote, or an
      upload answered without tags), since a remembered tag that the item no longer shows
      leaves the item where it is. Success deletes it; `412` leaves and forgets it; `400`
      blocks the row, the item still remembered.
    - `opened_placeholder` (the empty placeholder of an upload session this folder opened):
      success frees the name; `412` and `400` leave the row waiting (`upload-session-open`).
    - `finish` (the delete asked right after a bad upload, F200): anything but success or
      `404` leaves the item remembered for the next run.
    - `file_changed` (a file's delete answered `412`) uses the same function and cannot send
      an empty guard: an item read with no cTag is taken for changed before any request, and
      the row ends as restored (`restored`: the delete leaves the outbox, and a full cycle
      places OneDrive's version here again).
  - **What would close it**: no request with no guard (the row waits, or the item is left as
    someone else's), once it is known what OneDrive answers; each caller then says which.
