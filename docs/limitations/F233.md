- **F233. An upload step's file calls run in blocking sections, and a section that has begun ends by itself**
  (`upload/steps/sections.rs` `blocking`, `blocking_under`, `tree`; `upload/content.rs`; `upload/local.rs`;
  `upload/move_out.rs` and `upload/move_out/`; `folder/locks.rs` `InodeGuard::hold`; quality
  findings `UP6`, `X2`; the fill's side is F230). FRAGILE, *reasoned*, open. A row's step makes no call that can wait on
  the disk on a runtime thread: each run of file calls that used to follow each other with no
  wait between them is one section on a blocking thread. A section cannot be stopped once it
  has begun. What that leaves:
  - **A row dropped during a section is over before the section is, and the worker's stop
    waits for the section.** A row's task is dropped where it waits when the worker is stopped
    (`OutboxWorker::stop`: the sync stopping, a switch to read-only, a close that outlived its
    wait): `drain` ends the rows' tasks (`JoinSet::shutdown`). The section under way ends on
    its thread, and `drain` waits for every such section before it returns (`Sections`,
    `upload/steps/sections.rs`: each section of a row holds a share that `Sections::ended` waits for),
    so `stop` returns only when no file call of a row is running and no section holds the
    folder's descriptor. That is what it was when the calls ran on the row's own task. The
    sections that were there before this change (a read of content, the commits, the strips
    of a move out) are counted too; on `dev` a stop could return while one of them ran.
  - **Counted as well: the sections of a download a `move-out` row started** (`make_local`;
    the fill's own sections, F230). The share in the per-inode lock that such a section keeps
    carries a share in the worker's count (`folder::locks::holding_with`). Since `a9779f8` a
    stop could return while such a section ran: the tidying after a forced switch to
    read-only then found the file's lock taken (`try_lock` in `Tidy::tidy`) and left the
    placeholder outside the folder `hydrating`, with its attributes, its row dropped.
  - **How long a stop waits**: for the sections under way when it is asked, each one run of
    file calls (a write with its checkpoint, an `fsync`, a rename), as it waited when those
    calls ran on the row's task. A section takes nothing it could wait for from the one who
    stops: it makes file calls (no helper call, no lock but the folder's `Modes` mutex, which
    nobody holds across a wait), and the locks it has a share in were taken by its row
    before it began. Two sections also make one store call each (below); the store's thread
    waits for nothing a stopper holds. A row that waits for a lock is dropped there.
  - **One section can be long: the reopen for writing of a moved-out file** (`make_local`,
    `reopen_for_writing`). It is an open like any other, and by F91 it can wait for another
    opener's fill of the same file. It was a section before this change; the stop now waits
    for it, so a stop asked then lasts as long as that fill. No deadlock was found: nothing
    in `hydration/` or `helper/` takes `lifecycle`.
  - **A close that outlived its wait** (`OutboxWorker::close`, the daemon stopping) took the
    worker's handle, so the `stop` that cuts what is left does not wait for the worker at
    all, sections included. That is as it was.
  - **Not counted: what does not run on a row's task.** `protect`, `mark_tree` and the
    worker's marks run on the worker's own task, which is never dropped at a section (it
    stops at its token, between rows). `Tidy::dropped` runs on its caller's task (a switch to
    read-only, a Forget), and its sections end by themselves if that caller is dropped, as
    its sections did before; the ones added here only read.
  - **A section that changes the folder under a lock keeps a share in the lock until it
    ends** (`blocking_under`): the tree lock (the conflict copy's rename and strip, the
    rename that follows OneDrive's, the strip of a file uploaded again as new, a folder's
    commit step 1, the removal of a placeholder whose item went, the mark taken off after a
    move, a file's commit step 1) and the per-inode lock (a read of content, a file's commit
    step 1, the strip or removal of a file in the Trash, the removals inside a folder in the
    Trash). The share is let go of before the section stops counting for the stop.
    **Pinned in debug builds**: the functions that make these changes (`local::rename_to_copy`,
    `strip_found`, `remove_placeholder`, `commit_dir`, `commit_attributes`, `commit_id`, the
    rename of `follow_cloud`) assert that they run inside `blocking_under`
    (`local::assert_under_lock`), so a step that used a plain `blocking` for one fails every
    test that goes through it. Not pinned: the marks (`local::mark`, `clear_mark`, also used
    with no lock), and the sections of `move_out/`, whose strip and removals are shared with
    `Tidy`, which takes its locks inside its own section.
  - **Two sections record what they did, in the section** (`store.call_blocking`): the
    conflict copy (`steps::copy`: the rename, the strip, `outbox_copied`) and the upload as
    new (`steps::upload_as_new`: the strip, `outbox_orphan`). A stop never leaves a copy, or
    a stripped file, that the outbox does not know of: on `dev` the store call was queued in
    the same go as the file calls, and only a crash came between them. The rebase of the
    rows below a copied folder follows as a call of its own, as before.
  - **A section that only reads carries no share in the lock** it runs under (a state, a
    place, a name looked up): what it read is dropped with the row.
  - **A row dropped while a section runs does not start what followed it.** Where a run of
    file calls was followed by a store call with no wait between them, a stop could not come
    between the two (only where the store's queue made the call wait). Now it can, for as
    long as the section takes. The row stays `running` and is replayed at the next start, as
    after a crash at that point, which was possible before:
    - the object renamed to where OneDrive has it, and the rows below it not rebased, or the
      row not committed or given its new base (`steps::follow_cloud` and its two callers):
      nothing is lost, and the replay is not a plain repeat;
    - after such a rename in `steps::moved`, the mark taken off and the row not committed;
    - the placeholder removed, and the row not committed as gone (`steps::move_gone`): the
      replay finds no object and commits;
    - the mark taken off, and the move not committed (`steps::commit_move`);
    - the `uploading` mark written and the snapshot read, and the snapshot not kept
      (`content::run`);
    - a folder's directory opened, and the request not sent (`steps::mkdir`);
    - a moved-out object's path read, and `outbox_set_target` not written
      (`move_out::remember_place`).

    All but the first only repeat at the replay.
  - **A section the runtime does not run** (it is shutting down), or one that panics, fails
    the step as a local I/O failure, as a section that failed did before; where the answer was a
    plain yes or no it is now that failure (`move_out::run`'s proofs of a place: a failure
    never reads as "gone"). In `protect`, `mark_tree`, `unmark` and `Tidy`, which have no
    failure to give, it reads as the cautious answer (not downloaded, not found, stays
    marked, left as it is).
  - **Left on the runtime thread**, as calls that do not wait on a disk: `fstat` on an open
    descriptor (`InodeKey::of`, `Snap::of` before the last fragment, the kind and link count
    of a moved-out object), the `dup` of the root's descriptor (`Disk::dir("")`), the lease
    probe (`lease::open_for_writing`: two `fcntl`s) before the last fragment and before a
    moved-out file is reopened, and the hashing and copying of a fragment's bytes, which is
    computing. `Engine::stopped`, asked before each row and between fragments, is no file or
    store call: the user's pause is read from the store's memory of it (`Store::pause`, an
    atomic), and the hold from a mutex nobody keeps across a wait.
  - **Not done, outside the files of this change**: the worker's own loop still opens the
    folder (`Disk::open`) and reads each candidate's size by name (`local::size_at`) on a
    runtime thread (`upload/engine/drain.rs`), and so does the release of the rows waiting
    for space (`upload/space.rs` `release_fitting`). What the move out asks before it
    believes an `ESTALE` (`local::handles::current`) runs in a blocking section of its own
    (`upload/move_out/reach.rs`).
  - **A row's objects are shared, not duplicated**: `Found` keeps its directory in an `Arc`,
    and a moved-out object's descriptor is an `Arc<File>`, so a section adds no `dup` that
    could fail.
