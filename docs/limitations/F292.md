- **F292. What the reconcile makes the user's own waits for the disk once for each object with an id**
  (`konedrived/src/folder/disk.rs` `outside`; `remote/materialize/rw.rs` `copy_aside`;
  `remote/materialize/removal.rs` `remove_whole`, `stays`; `konedrive-fs/src/placeholder.rs`
  `strip`; quality finding `UP7`) — the six strips of the reconcile go through the one strip
  of the code base: the item id, `fsync`, then the rest. Before, they took the attributes off
  in the order the filesystem lists them, with no `fsync`, so a daemon that died between two
  of them could leave a file with its id and no state, which the helper answers with `EIO`.
  Now the id is the first to go: whatever is left after it is on an object that is the
  user's own. The price is one `fsync` for each object that carried an id:
  - a rescue (`Disk::rescue`, read-only mode): one for the file; for a directory, one for
    each directory and each downloaded file with an id below it, none for a file that is
    not downloaded (it is removed, not rescued) or for one with no id. A rescued directory
    with D directories and F downloaded files of ours costs D + F;
  - a conflict copy (`copy_aside`, read-write mode): one, for the object itself; what is
    below a copied directory is not touched;
  - a removal where something stays (read-write mode): one for each downloaded file that
    stays and each folder that stays with it.

  All of it runs inside the reconcile's apply, on a blocking thread (`spawn_blocking`), with
  the folder's lease held; the tree lock is held too only in a read-write folder, as `F262`
  says of the examination (a rescue in a read-only folder holds the lease only). Not measured
  here; `F262` measured about 1 ms an
  object on Btrfs on an NVMe disk (debug build) and expects ten times that on a rotating
  disk. That figure is for files: the `fsync` of a directory just after its rename
  may cost more on Btrfs, not measured. Where it buys least: what a rescue moved out of the folder is intercepted only as
  long as the helper keeps the marks of the directories moved with it (`Disk::rescue` asks
  for no `UnmarkDir`), and marks do not outlive a restart of the machine, so there the order
  closes the window (the daemon dies, the helper lives) and the `fsync` adds nothing known.
  It is kept all the same: a strip with the same order and no `fsync` would be the second
  strip `UP7` removed.
  A disk that refuses the `fsync` now fails the strip: a conflict copy or a removal that
  keeps something then fails the apply, and the cycle with it, where it went through before;
  a rescue counts the entry as passed over and goes on, as for any other failure there.
  What the next cycle sees then: the id is already off, so it finds an object of the user's
  own. The bytes stay, and the cycle cannot fail for ever (no id, so no `fsync` the next
  time). But what follows the strip is skipped for good: in `remove_whole` the folder is not
  listed as made again (`recreated`, from which `outbox_detach_parents` is called); in
  `copy_aside` the rows below a copied directory are not re-based (`OutboxOp::Rebase`) and
  the copy is not listed (`copies`, `examine`). What that does to the outbox rows was not
  traced. The same class as the third window of `F293`.
