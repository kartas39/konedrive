- **F116. What OneDrive removed goes from the disk in the cycle, but for what it never had** (`konedrived/src/remote/materialize/removal.rs`,
  `take_off`, policy `Removed`; write design §9 "What OneDrive removed"; issue #104, the owner's ruling
  of 2026-10-04) — a read-write reconcile takes off the disk, under an item removed in OneDrive, what
  OneDrive had and the daemon placed: files not downloaded, the removed items' own downloads unchanged
  since, a download in progress (stopped first), folders with nothing left in them. It keeps what only
  this computer has, with the folders above it:
  - a file with no item id, whatever its name, but for an empty file with an ignored name;
  - a directory with no item id and an ignored name that holds anything, as it is, not looked into;
  - a download that is changed here (its stamp differs, it is open for writing, or an `update` row
    waits for it), or that carries an id which is not of the removed item or of what the base has
    below it (moved in from another folder, not examined yet);
  - a file with an id whose state cannot be read and that holds data.
  What is kept loses konedrive's attributes and is handed to the examination: the files go up as new,
  the folders are made again in OneDrive. The outbox rows that would still upload, create or move
  something there are dropped (not a running one, nor a removal), and the examination records new ones.
  - **What keeps no folder.** A symlink, a socket, an empty file or an empty directory with an ignored
    name stay only where their folder stays for another reason; in a folder that goes they are
    removed with it. An empty folder made here goes.
  - **A folder kept only by what is never uploaded** (F243) is still made again in OneDrive, empty.
  - **"Changed here" is the stamp, the write lease and the row**, not the hash: a download rewritten
    with the same content and a new time is kept and uploaded as new. A file open for reading only is
    not kept; the program keeps the unlinked inode. Between the look at a file that does not stay and
    its unlink a program can still open it for writing; the lease is not held across the unlink (a
    lease would only delay that opener, who would then hold the unlinked inode).
  - **Before anything goes**, the store forgets the local object of everything found there (the item,
    what the tree has below it, and every object, by its own id and handle), so no examination can
    prove one of them gone.
  - **An object that will not go** (an I/O error, a directory the daemon may not write) fails the
    cycle, and the cycle's tree rows are not committed: `items` keeps the item, and the next cycle
    tries again. What was done before stays: the objects forgotten, the rows dropped, the attributes
    off what is kept. A forgotten object makes the item unproven, never deleted; a download stopped
    in a file that stays is a placeholder again (F191). What is kept is handed to the watcher, the
    rows wait for the folders made again, and the Activity entry is written, on the failing cycle
    too — when the reconcile fails and when its commit does; not when the daemon stops in between, nor when
    the reconcile's blocking task panics: then the next Full local scan finds the files, as it finds
    any new file. A store failure while the rows are let wait for the folders made again
    (`outbox_detach_parents`) is only warned of and not tried again: such a row keeps the removed
    folder as its parent and is answered by OneDrive. A filesystem mounted
    inside the removed folder is not entered: it stays, with the folders above it, as what is kept
    on this computer only does (F194).
  - **One activity entry** (`removed`) is written for the outermost thing removed, saying how many
    files go up as new and how many items stay on this computer only. A cycle that fails writes it
    only where it took the attributes off something in that cycle (a file, or the folder itself), so
    a cycle failing again and again says it once. What lost its id is the user's own from then on and
    is not taken off again: the cycle that goes through later does not say it a second time. It does
    say it again where the removed folder still carried its id (the failure came before the folder's
    own turn), with everything that stays in it.
    What stays of something taken off in the holding directory is said under the path it was moved
    from when this run moved it, else under `.konedrive-holding/<id>`.
  - `resyncChangesUploadDifferences` (§3.7) keeps every download as well, changed or not: that listing
    does not say the items were removed.
