- **F116. What OneDrive removed goes from the disk in the cycle, but for what it never had** (`konedrived/src/remote/materialize/removal.rs`,
  `take_off`, policy `Removed`; write design §9 "What OneDrive removed"; issue #104, the owner's ruling
  of 2026-10-04) — a read-write reconcile takes off the disk, under an item removed in OneDrive, what
  OneDrive had and the daemon placed: files not downloaded, downloads unchanged since, a download in
  progress (stopped first), folders with nothing left in them. It keeps what only this computer has: a
  file with no item id, and a download that is changed here (its stamp differs, it is open for writing,
  or an `update` row waits for it), with the folders above them; a file with an id whose state cannot
  be read and that holds data is kept too. What is kept loses konedrive's attributes and is handed to
  the examination: the files go up as new, the folders are made again in OneDrive. The outbox rows
  that would still upload, create or move something there are dropped (not a running one, nor a
  removal), and the examination records new ones.
  - **What does not keep a folder.** An ignored name, a symlink, a socket stay only where their folder
    stays for another reason; in a folder that goes they are removed with it. An empty folder made here
    goes. A file whose name OneDrive refuses stays and keeps its folder, though it is never uploaded.
  - **"Changed here" is the stamp, the write lease and the row**, not the hash: a download rewritten
    with the same content and a new time is kept and uploaded as new. A file open for reading only is
    not kept; the program keeps the unlinked inode.
  - **Inside a folder that is leaving the item still goes whole** (policy `RemovedLeaving`,
    `remote/materialize/rw/leaving.rs`): what would stay there would be examined by the leaving
    folder's own rules (F188). It goes with the leaving rows.
  - **Before anything goes**, the store forgets the local object of everything found there (the item,
    what the tree has below it, and every object, by its own id and handle), so no examination can
    prove one of them gone.
  - **An object that will not go** (an I/O error, a directory the daemon may not write) fails the
    cycle, and the cycle's tree rows are not committed: `items` keeps the item, and the next cycle
    tries again. What was done before is committed already and stays — the objects forgotten, the
    rows dropped, the attributes off what is kept — and that is safe: a forgotten object makes the
    item unproven, never deleted; a file whose attributes are off is the user's own and goes up as
    new; a download stopped in a file that stays is a placeholder again (F191). A filesystem mounted
    inside the removed folder is not entered, so its mount point fails the cycle until it is unmounted.
  - **One activity entry** (`removed`, with how many files were kept) is written for the outermost
    thing removed. After a hand-over from a Changed to a Full reconcile it can be written twice.
  - `resyncChangesUploadDifferences` (§3.7) keeps every download as well, changed or not: that listing
    does not say the items were removed.
